# Privacy Policy (Sprint 6 draft — NOT legal advice, needs real legal review)

> **This is an engineering-authored draft describing what data this system actually processes, not a legally reviewed Privacy Policy.** Publishing this (or any privacy policy) without review by a lawyer familiar with your jurisdiction and the jurisdictions of the people whose data you process (GDPR for EU residents, CCPA/CPRA for California residents, etc.) is a compliance risk. Use this as an accurate factual starting point for that review, not as a finished document.

## What data this system collects and why

MakeAble discovers public business contact information for content creators, in order to send them collaboration/partnership outreach on behalf of brands using this platform.

| Data | Source | Purpose | Where it's stored |
|---|---|---|---|
| Creator handle, platform, niche | `apps/backend`'s search pipeline (official platform sources only — `docs/SECURITY.md` "Why the original scraper was replaced") | Identify and categorize creators for outreach matching | `public` Postgres schema, `Creator` table |
| Creator bio, social links, website URL | Extracted from the creator's own publicly-published page (`apps/python/extractor`) | Personalize AI-generated outreach | `public` schema, `Creator` table |
| Creator business email | Extracted from the creator's own publicly-published page, validated (syntax + MX + disposable-domain check) before storage | The actual outreach destination | `public` schema, `Email`/`ValidationResult` tables |
| AI-generated draft content (summary, brand-fit analysis, email subject/body) | Generated by `apps/ai` from the above creator data + brand info supplied by the platform operator | Personalized outreach content, held for human review before any send | `ai` Postgres schema |
| Campaign/send records, delivery events (sent/delivered/bounced/opened/clicked/replied) | `apps/email`, recorded as campaigns are sent and providers report delivery status | Track outreach effectiveness, enforce suppression/dedup guarantees | `email` Postgres schema |
| Suppressed/unsubscribed addresses | Manual entry or automatic (bounce/complaint webhook) | Ensure suppressed addresses are never contacted again | `email` schema, `suppression_list` table |
| Admin user accounts (email, hashed password, role) | Created via `npm run seed:admin` or by an existing admin | Authenticate access to the internal dashboard | `admin` Postgres schema |
| Audit log (who did what, when) | Every mutating action taken through `apps/admin` | Accountability/audit trail for internal operations | `admin` schema, `audit_log` table |

**Explicitly not collected**: private/non-public creator information, data scraped from search-result snippets without visiting the source page, any data from a creator's private/DM inbox, payment information (this system has no billing feature).

## Data retention

Not currently time-bounded in code — there is no automatic deletion/expiry job for any of the tables above. **This is a gap to close before real production use with real people's data**: define and implement a retention policy (e.g., "delete creator records not contacted in N years," "purge audit logs after N years") appropriate to your jurisdiction's requirements and your own data-minimization commitments.

## Third parties this data may be shared with

- **AI providers** (OpenAI/Anthropic/Gemini, whichever `apps/ai`'s `AI_PRIMARY_PROVIDER`/`AI_FALLBACK_PROVIDER` are configured to use): creator bio/summary/brand info is sent to whichever provider is active, to generate draft content. Each provider's own data-handling/retention policy applies to that transmission — link to the specific provider's policy once real (non-mock) keys are configured for production use.
- **Email providers** (SMTP/Resend/SES/SendGrid, whichever a campaign's `SenderProfile` names): recipient email address + draft subject/body are transmitted to send the actual message. Same caveat — link to the specific provider's policy once configured.
- **Hosting infrastructure** (Supabase/Postgres, Upstash/Redis): all persistent data above lives in these two managed services. Their own data-processing agreements apply.

## Data subject rights (creators whose contact info is processed)

Not currently implemented as a self-service feature. A creator wanting their data removed would need to be identified manually (by email or handle) and deleted via direct database access, or a bespoke script — there is no "delete my data" API endpoint in this system today. **This is a gap to close** if operating under a regime (GDPR, CCPA) that grants a legal right to erasure/access, not merely a nice-to-have.
